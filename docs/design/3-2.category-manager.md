# カテゴリ管理テーブル設計書

## 1. 目的と対象範囲

カテゴリをデータベースで管理し、`data/publish/index.html` のカテゴリ一覧を親見出し・小見出しの2階層で表示する。表示順はカテゴリテーブルで指定する。

本書は従来の `parent_name` / `child_name` を同じ行に持つ案を置き換える。テーブル・DBマイグレーション・GoストアのCRUD、および管理画面での一覧表示・追加・編集・削除は実装済み。公開HTML生成処理の対応は後続作業とする。

## 2. 現状と設計方針

導入前のDBにはカテゴリテーブルがなく、記事の `blogs.category` にカテゴリ文字列を保存している。公開出力は引き続き `internal/publish/usecase.go` の `buildIndexCategories` で公開記事からカテゴリを抽出し、文字列中の `/` や `-` から階層を推測して名前順に並べている。

新設計では以下を採用する。

- `categories` の1行を1つの見出しとする。
- `is_heading = 1` を親見出し、`is_heading = 0` を小見出しとする。小見出しの `parent_id` は親見出しのIDまたはNULL（親なし）とする。
- 親見出しだけの登録も可能とする。3階層以上は許可しない。
- `sort_order` は同じ親を持つカテゴリ内での表示順とする。親なしの通常カテゴリと親見出しは同じ最上位グループ内で並べ替える。子カテゴリは同じ親の中で並べ替える。
- 表示名と既存記事のカテゴリ値を分け、名前の変更や階層の移動で既存記事・URLとの対応が失われないようにする。
- 1記事につき1カテゴリという既存仕様を維持する。

## 3. categories テーブル

| カラム名 | SQLite型 | NULL | 既定値 | 内容 |
| --- | --- | --- | --- | --- |
| id | INTEGER | 不可 | 自動採番 | 主キー。カテゴリの識別子 |
| parent_id | INTEGER | 可 | NULL | 親見出しのID。親なし小見出し・親見出しはNULL |
| is_heading | INTEGER | 不可 | 0 | 1なら親見出し、0なら小見出し。親見出しはparent_idがNULL |
| name | TEXT | 不可 | なし | その階層だけの表示名（例：技術、Go） |
| category_key | TEXT | 不可 | なし | 旧データの照合にも使用する一意で不変の内部キー |
| sort_order | INTEGER | 不可 | 0 | 同じ親の中での表示順。0以上の整数 |
| created_at | TEXT | 不可 | なし | 作成日時。アプリケーションからUTCのRFC3339形式で設定 |
| updated_at | TEXT | 不可 | なし | 更新日時。同形式で更新時にアプリケーションから設定 |

### 3.1 親子関係と制約

- `parent_id` は `categories.id` を参照する自己参照外部キーとする。
- 親の削除は `ON DELETE RESTRICT` とし、小見出しを残したまま親見出しを削除できないようにする。
- 小見出しの親は親見出しに限る。自分自身を親にする操作、小見出しを親にする操作、子を持つ親見出しを小見出しにする操作は禁止する。
- 表示名は前後の空白を除去した空でない文字列とする。Unicodeの空白除去はアプリケーション側でも検証する。
- 表示名は兄弟内で一意とする。異なる親見出し配下では同名の小見出しを許可する。
- `category_key` は全体で一意とし、登録後の変更を許可しない。表示名に階層区切り文字が含まれていても、階層判定には使用しない。
- `sort_order` の重複を許可し、同値の場合は `id` 昇順とする。名前を変えても表示順は変わらない。
- SQLiteにはテーブルの暗黙の表示順がないため、取得時に必ず `ORDER BY` を指定する。

### 3.2 DDL案

```sql
CREATE TABLE categories (
  id INTEGER PRIMARY KEY,
  parent_id INTEGER DEFAULT NULL,
  is_heading INTEGER NOT NULL DEFAULT 0
    CHECK (is_heading IN (0, 1) AND (is_heading = 0 OR parent_id IS NULL)),
  name TEXT NOT NULL CHECK (length(trim(name)) > 0 AND name = trim(name)),
  category_key TEXT NOT NULL UNIQUE CHECK (length(trim(category_key)) > 0),
  sort_order INTEGER NOT NULL DEFAULT 0
    CHECK (typeof(sort_order) = 'integer' AND sort_order >= 0),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  CHECK (parent_id IS NULL OR parent_id <> id),
  FOREIGN KEY (parent_id) REFERENCES categories(id) ON DELETE RESTRICT
);

-- NULL同士は通常のUNIQUEでは重複判定されないため、親の有無で分ける。
CREATE UNIQUE INDEX idx_categories_root_name
  ON categories (is_heading, name) WHERE parent_id IS NULL;

CREATE UNIQUE INDEX idx_categories_child_name
  ON categories (parent_id, name) WHERE parent_id IS NOT NULL;

CREATE INDEX idx_categories_parent_sort
  ON categories (parent_id, sort_order, id);

-- CHECKでは他の行を参照できないため、2階層の制限はトリガーで保証する。
CREATE TRIGGER categories_check_parent_insert
BEFORE INSERT ON categories
WHEN NEW.parent_id IS NOT NULL
BEGIN
  SELECT RAISE(ABORT, 'parent must be a root category')
  WHERE NOT EXISTS (
    SELECT 1 FROM categories
    WHERE id = NEW.parent_id AND parent_id IS NULL
  );
END;

CREATE TRIGGER categories_check_parent_update
BEFORE UPDATE OF parent_id ON categories
WHEN NEW.parent_id IS NOT NULL
BEGIN
  SELECT RAISE(ABORT, 'parent must be a root category')
  WHERE NOT EXISTS (
    SELECT 1 FROM categories
    WHERE id = NEW.parent_id AND parent_id IS NULL
  );
  SELECT RAISE(ABORT, 'category with children must remain a root')
  WHERE EXISTS (SELECT 1 FROM categories WHERE parent_id = OLD.id);
END;

CREATE TRIGGER categories_keep_key
BEFORE UPDATE OF category_key ON categories
WHEN NEW.category_key IS NOT OLD.category_key
BEGIN
  SELECT RAISE(ABORT, 'category_key is immutable');
END;
```

外部キーはすべてのDB接続で `PRAGMA foreign_keys = ON` を有効にする。`Store.New` の接続DSNに `_pragma=foreign_keys(1)` を指定し、コネクションプール全接続で保証する。主キーの更新は管理機能として提供しない。

## 4. データ例と表示順

| id | parent_id | name | category_key | sort_order |
| --- | --- | --- | --- | --- |
| 1 | NULL | 技術 | 技術 | 10 |
| 2 | 1 | Go | 技術-Go | 20 |
| 3 | 1 | SQLite | 技術-SQLite | 10 |
| 4 | NULL | 日記 | 日記 | 20 |

表示結果：

```text
技術
  SQLite
  Go
日記
```

親見出しは `sort_order, id` 順、小見出しは各親見出しの配下で `sort_order, id` 順に表示する。小見出しの `sort_order` が他の親見出しより小さくても、所属する親見出しの配下から移動しない。

取得SQL例：

```sql
SELECT
  root.id AS root_id, root.name AS root_name,
  root.category_key AS root_key,
  child.id AS child_id, child.name AS child_name,
  child.category_key AS child_key
FROM categories AS root
LEFT JOIN categories AS child ON child.parent_id = root.id
WHERE root.parent_id IS NULL
ORDER BY root.sort_order, root.id, child.sort_order, child.id;
```

`LEFT JOIN` により、小見出しのない親見出しも取得できる。アプリケーションでは `root_id` 単位にまとめて表示用データを組み立てる。

## 5. 記事との関連と公開HTMLの扱い

記事の `blogs.category` と `blogs.parent_category` には表示名を保存する。内部では `blogs.category_id` と `blogs.parent_category_id` を使ってカテゴリを識別し、親が異なる同名カテゴリや親なしカテゴリを区別する。両IDはNULL可で `categories.id` を参照し、使用中カテゴリの削除は制限する。

- 記事保存時は選択された登録済みカテゴリをIDに対応付ける。カテゴリの作成・追加は行わず、未登録の指定はHTTP 400（CATEGORY_NOT_FOUND）として保存を拒否する。
- 親なしの選択は仮想親「親見出しなし」配下の登録済みカテゴリに対応付ける。親のみの選択も許可し、両方空の場合はIDもNULLにして未選択として保存する。
- 登録済みカテゴリの旧キーが渡された場合は表示名とIDへ変換する。名前での一致を優先し、キーは互換入力として扱う。
- カテゴリ名変更時はDBトリガーで、そのIDを参照する記事の親見出し名またはカテゴリ名と更新日時を変更する。公開・非公開の両方を対象とし、別の親や親なしグループの同名カテゴリには影響しない。
- 記事保存とカテゴリIDの関連付け、カテゴリ名変更と記事側の変更は、それぞれ同じトランザクションで完了する。途中失敗時はすべて元に戻す。
- 親見出し名・カテゴリ名はカテゴリ管理画面と同じ表示名を扱えるようにし、従来のキー用の文字種制限・20文字制限は適用しない。前後の空白は除去する。
- カテゴリ一覧の表示対象と順序は `categories` から決め、記事が0件でも表示する。カテゴリが空なら空状態を表示する。

公開HTMLの再生成は従来の `publish` 操作で行う。公開生成処理をカテゴリテーブルに切り替える対応は後続作業であり、現行処理は記事のカテゴリ文字列からカテゴリページとURLを生成する。表示名の変更・旧キーからの正規化は、次回の公開生成時に公開ページの表示名やカテゴリURLにも反映される。

## 6. 既存データの移行方針

1. バージョン管理されたマイグレーションでテーブル・インデックス・トリガーを作成する。
2. 公開・非公開を含めた `blogs.category` の空でない値を重複排除し、各値を `category_key` とした親見出しとして登録する。`name` は前後の空白を除去した値とし、空になる値や同名になる値は移行前に検出して対応を決める。
3. 初期順序は既存値の名前順（SQLite BINARY順）に10刻みで設定する。移行時の日時を両日時カラムに設定する。
4. 必要な親見出しを追加し、既存カテゴリの `parent_id`・`name`・`sort_order` を設定して2階層へ整理する。`-` や `/` を含む既存値を機械的に分割しない。
5. 同じトランザクションで移行を完了する。初期データ投入は一度だけ行い、アプリ起動のたびに削除済みカテゴリを復元しない。
6. 後続の公開生成実装が完了した段階で `publish` を実行し、`data/publish/index.html` とカテゴリページへ反映する。

実装は `internal/store/migrations/001_categories.sql` と `category_migration.go` に配置する。`store_migrations` テーブルのバージョン `001_categories` で適用済み状態を管理し、`Store.New` で未適用の場合のみ実行する。空白だけの既存値や、空白除去後に同名となる既存値がある場合は移行をロールバックし、対象値を含むエラーを返す。

ストアは `CategoryEntity` と `ListCategories`・`GetCategory`・`CreateCategory`・`UpdateCategory`・`DeleteCategory` を提供する。一覧は親見出しの直後にその小見出しを並べた順序で返す。更新時の空の `CategoryKey` は既存キーを維持する指定とする。利用中の削除は `ErrCategoryInUse`、存在しないIDの取得・更新・削除は `sql.ErrNoRows` を返す。

`005_blog_category_links` で既存記事のカテゴリ値を表示名へ正規化し、IDで関連付ける。公開HTMLは自動生成せず、従来のpublish操作で反映する。

## 7. 後続実装の確認観点

- 親見出し同士と、各親見出し内の小見出しを独立して並べ替えられる。
- 同順序ではID順となり、表示名を変えても順番が安定する。
- 3階層、自分への参照、循環、子を持つ親の小見出しへの移動を拒否する。
- 存在しない親への参照、子を持つ親の削除、兄弟内の同名登録を拒否する。
- 負数・小数の表示順、空の表示名、キーの重複・変更を拒否する。
- 小見出しがない親、記事がないカテゴリ、親自身にも記事がある場合を表示できる。
- 移行で既存記事の本文・日時が維持され、同じ移行を再起動時に繰り返さない。
- 表示名・階層変更後もキーにより記事を取得できる。

## 8. カテゴリ一覧APIと管理画面

`GET /admin/api/categories` は `{"items": [...]}` 形式で `CategoryEntity` の一覧を返す。順序はストアの `ListCategories` に従い、親見出しの直後に配下の小見出しを表示順・ID順で並べる。記事の有無で絞り込まない。未登録の場合は `items: []`、取得に失敗した場合は既存の管理APIと同じ形式でHTTP 500を返す。

管理画面の `#/categories` はページ表示時にAPIから一覧を取得し、カテゴリ名と操作ボタンを表示する。階層・表示順・更新日のカラムは一覧に表示しない。小見出しを字下げして親子を区別し、APIの順序を維持する。読み込み中・未登録・取得失敗を区別し、取得失敗時は再読み込みボタンを表示する。

表示上は、`is_heading = 1` のカテゴリを子の有無によらず親見出しとし、既存データとの互換性のため小見出しを持つカテゴリも親見出しとして扱う。`parent_id IS NULL` かつ親見出しではないカテゴリは一覧末尾の仮想親見出し「親見出しなし」にまとめ、小見出しとして表示する。各グループ内の順序はAPIの順序を維持する。仮想親は該当カテゴリがある場合のみ表示し、DBへ保存せず、件数にも含めない。仮想親には小見出し追加のみを用意し、編集・削除は提供しない。配下の実カテゴリは通常どおり編集・削除できる。小見出し追加ボタンは表示上の親見出し行だけに表示し、「親見出しなし」配下を含む小見出し行には表示しない。

一覧の表題右側に「親見出しを追加」、親見出し行の右端に「カテゴリを追加」を配置する。一覧には編集・削除ボタンを表示せず、カテゴリ行のクリックまたはEnter・Spaceキーで編集フォームを開く。並べ替え・小見出し追加ボタンの操作では行編集を開かない。編集フォームには「削除」ボタンを表示し、新規追加フォームには表示しない。追加フォームではカテゴリ名のみ入力し、表示順は兄弟内の最大値+10を自動設定する。削除前に確認を表示し、操作中の連打を防ぐ。成功時は一覧を再取得する。

`POST /admin/api/categories` は `name`・`parent_id`（親見出しと親なし小見出しはnull）・`is_heading`・`sort_order` を受け取り、HTTP 201で作成後のカテゴリを返す。キーはサーバーで `category-` + UUIDとして生成する。同階層の同名はHTTP 409、空名・負の表示順・親見出し以外の親はHTTP 400とする。

`DELETE /admin/api/categories/{category_id}` は削除後に `id`・`result: "deleted"` を返す。記事で使用中のカテゴリや小見出しを持つ親見出しはHTTP 409、存在しないIDはHTTP 404、不正なIDはHTTP 400とする。

各カテゴリ行のクリックで、カテゴリ名を入力済みのフォームを開く。表示順の入力欄は表示せず、保存時は既存の表示順を送信して維持する。「保存する」で `PUT /admin/api/categories/{category_id}` に `name`・`sort_order` を送信し、HTTP 200で更新後のカテゴリを返す。親子関係・キー・作成日時を維持し、記事で使用中のカテゴリも編集できる。同階層の同名はHTTP 409、不正な入力はHTTP 400、存在しないIDはHTTP 404とする。保存後に一覧を再取得して表示順にも反映する。

実カテゴリの各行に「上へ」「下へ」を表示する。通常の親見出し同士、同一親の小見出し同士、仮想親「親見出しなし」配下同士をそれぞれ独立して1つずつ移動する。先頭の「上へ」と末尾の「下へ」は無効化する。仮想親自体は移動対象にしない。親見出しの移動では配下の小見出しもまとまって表示位置が変わる。

`POST /admin/api/categories/{category_id}/move` は `direction: "up" | "down"` を受け取る。トランザクション内で兄弟を `sort_order, id` 順に取得して隣接要素を交換し、対象グループの表示順を0から10刻みで振り直す。同順序の既存データでも移動を確実に反映し、途中失敗時は全更新をロールバックする。先頭・末尾を越える操作は変更なしで成功とする。不正なID・方向はHTTP 400、存在しないIDはHTTP 404、成功時はHTTP 200で `result: "moved"` を返す。画面は成功後に一覧を再取得する。

## 9. 記事の親見出し

`blogs.parent_category` は `TEXT NOT NULL DEFAULT ''` とし、Goの `BlogEntitty.ParentCategory`、管理APIの `parent_category` に対応する。親がない場合は空文字とする。親見出しの検索用に `idx_blogs_parent_category` を追加する。

`002_blog_parent_category` マイグレーションで既存DBにカラムを追加し、登録済みの小見出しに属する記事は親の `category_key` で一度だけ補完する。親見出しのみ・未登録カテゴリ・未分類の記事は空文字のままとし、カテゴリ文字列から親を推測しない。

ストアは旧カテゴリキーだけが渡された場合に親見出しを補完する。管理APIで明示的に `parent_category: ""` を送った場合は親なしとして扱う。既存クライアントが親見出しを省略し、記事のカテゴリも変えずに更新した場合は保存済みの値を維持する。seedも `parent_category` を指定でき、省略時は同じ補完処理を使う。

カテゴリの削除判定では `blogs.category_id` と `blogs.parent_category_id` の両方を参照し、どちらかで使用中なら削除を拒否する。記事編集画面は親見出し・カテゴリを一つのセレクトボックスに統合する。カテゴリ一覧APIから選択肢を取得し、「親見出し > 子カテゴリ」で表示する。親なしは「親見出しなし > カテゴリ名」、親のみは親見出し名で表示する。「未分類」は両項目を空文字にする。読み込み・保存・ローカル下書きの保存と復元に対応し、既存値が一覧にない場合も現在の設定として表示して維持する。取得失敗時は再読み込みを提供する。About編集では表示しない。公開HTMLへの表示は後続作業とする。

## 10. 親見出し区分の保存

`003_category_heading` マイグレーションで `categories.is_heading` を追加する。既存の親として使われている行を1にし、その他の既存行は0として表示を維持する。新規作成時は「親見出しを追加」から1、各親および仮想親からの「カテゴリを追加」から0を送信する。APIで省略した場合は親なしを親見出しとして扱う。編集では区分を維持し、最後の子を削除しても親見出しとして残る。並べ替えでも、子がない親見出しを通常の親見出しと同じグループに含める。

## 11. 親見出しと親なしカテゴリの同名登録

`004_category_name_scope` マイグレーションで、親なし行の一意インデックスを `(is_heading, name)` に変更する。親見出しと仮想親「親見出しなし」配下のカテゴリは、同名でも別々に登録・編集できる。親見出し同士、親なしカテゴリ同士、および同じ親に属するカテゴリ同士の同名登録は引き続き拒否する。

## 12. 記事とカテゴリの同期マイグレーション

`005_blog_category_links` で `blogs.category_id`・`blogs.parent_category_id`（いずれもINTEGER、NULL可、categories.idへの外部キー、ON DELETE RESTRICT）と各IDの検索インデックスを追加する。既存記事も名前または旧キーから照合し、未登録の親・カテゴリを作成して対応付ける。移行時は記事の本文・公開日・更新日時を維持する。全体を一つのトランザクションで実行し、失敗時はカラム追加・カテゴリ作成・記事更新・移行記録をすべてロールバックする。

`categories_sync_blog_names` トリガーにより、管理APIだけでなくseed等からのカテゴリ名更新でも、関連する記事を同じトランザクションで更新する。カテゴリキーは変更しない。

## 13. 記事保存時のカテゴリ自動追加の廃止

記事編集で登録済みの選択肢を使うため、通常保存のカテゴリ解決処理は読み取り専用とする。親見出し・カテゴリの新規作成や区分変更は行わない。未登録・削除済み・親子の組み合わせ不一致の選択は入力エラーとし、既存記事の内容も変更しない。未選択保存と、カテゴリ名変更時の記事への連動更新は維持する。

既存DBの初回移行（005）に限り、過去の記事を失わず関連付けるための登録処理を残す。seedはcategories.jsonで必要なカテゴリを事前に定義し、通常の記事保存の自動追加には依存しない。

## category_key の廃止（006）

`006_remove_category_key` で `categories.category_key` とその不変制約を削除する。上記のキーに関する記述・DDLは旧仕様の移行経緯として残す。既存DBは005までの移行で記事のカテゴリを表示名・関連IDへ変換してから006を適用する。カテゴリID・親ID・表示順・日時と記事の関連IDは維持する。現在のカテゴリAPIはキーを返さず、記事保存は親と表示名で照合する。

シードの `category_key`・`parent_key` はファイル内の参照名としてのみ利用する。DB再投入時は親ID・見出し種別・表示名で照合し、既存IDを保って表示順を更新する。表示名変更・親移動の照合には使わない。

## 通常カテゴリと親見出しの表示順

管理画面では親なしの通常カテゴリと親見出しを同じ最上位グループとして表示順・ID順に並べる。通常カテゴリを一覧末尾の仮想親へまとめる従来の表示は廃止する。「上へ」「下へ」は最上位で種別を問わず移動し、子カテゴリは同じ親の中だけで移動する。親見出しの移動時には子もまとまって表示位置が変わる。最上位の追加時の表示順は種別を問わず最上位の最大値+10とし、「通常カテゴリを追加」ボタンで親なしの通常カテゴリを作成する。公開トップページも同じ登録済み表示順を使用する。
