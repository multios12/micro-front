# アクセスレポートCLI 設計案

## 目的

CaddyのJSONアクセスログを解析し、どの記事にアクセスがあるかを確認する静的HTMLレポートを生成する。

本書はアクセスレポートCLIの設計資料。実装は `cmd/access-report/` にまとめ、既存の公開処理から独立している。現在の利用方法・引数・環境変数は [access-report README](../cmd/access-report/README.md)、実装の制限は末尾の「実装済みの使い方」を参照する。

テーブル設計：[アクセスレポート テーブル設計案](access-report-tables.md)。画面確定後の集計・保存・期間の仕様は、このテーブル設計で具体化する。

## 基本方針

- 同じリポジトリ内に独立したCLIを追加する。
- ソースとテンプレートを `cmd/access-report/` 内にまとめ、`internal/` 配下には追加しない。
- micro-frontの管理画面・公開処理から独立する。記事DBはタイトル表示のために任意で読み取り専用参照する。
- 初回は全件、以降はログの追記部分を取り込み、保存済み集計から静的HTMLを生成する。
- 公開ページへのJavaScript追加や、解析用の常駐サーバーは必要としない。
- 記事アクセス数・ユニークアクセス数・日別推移・記事ランキング、およびクローラー・404一覧を出力する。

アクセス数は記事ページに対するリクエストの集計であり、実際の読者数、読了数、滞在時間を表すものではない。

## ディレクトリ構成

```text
cmd/
  micro-front/             # 既存プログラム
  access-report/
    main.go                # 引数処理、入出力の準備、実行
    log.go                 # JSONログの読み込み、必要項目の抽出
    aggregate.go           # URL判定、除外、日別・記事別集計
    state.go               # 専用SQLite、差分状態と集計の保存
    report.go              # テンプレートへの受け渡し、HTML出力
    templates/
      report.tmpl          # レポートテンプレート
      styles.tmpl          # スタイル定義
    *_test.go              # 集計条件や入力処理のテスト

data/
  publish/                 # 既存の公開サイト
  access-report/
    index.html             # レポート出力例
  access-report-state/
    state.db               # 集計と差分状態
    state.db.visitor.key   # ユニーク判定用HMAC鍵（公開対象外）
```

Goのソースは同じ `package main` とし、役割ごとにファイルを分ける。リポジトリ直下の `go.mod` を共有し、別モジュールにはしない。テンプレートは `go:embed` でバイナリへ埋め込む。

## 処理の流れ

```text
入力ファイル一覧の確定
  → JSONログを1行ずつ読み込み
  → 対象ホスト・HTTPメソッド・ステータス・記事URLを判定
  → 除外条件を適用
  → 日別・記事別に集計し、処理済み位置と同時に保存
  → 保存済み集計を表示期間で抽出
  → 静的HTMLを生成
```

ログ全体をメモリへ読み込まず、行単位で処理する。メモリ上には集計値と入力処理の件数を保持する。

## 入力

### 対応形式

- Caddyのアクセスログを想定した、1行につき1つのJSONオブジェクト。
- 通常のログファイルとgzip圧縮済みログファイル。
- 複数ファイルを指定可能とし、ローテーション済みログも入力に含める。

主に使用する項目は `ts`、`request.host`、`request.method`、`request.uri`、`status` とする。除外設定を使用する場合は、User-Agentと接続元情報も参照する。項目の実際の形と意味は、利用中のCaddy設定とログサンプルで確認する。

### 入力ファイルの扱い

- `--input` を複数回指定できるものとする。
- 同じファイルの重複指定は検出してエラーにする。
- 別ファイル間に含まれる同一リクエストの重複は、自動排除しない。異なるリクエストを誤って消さないため、重複しないログ一式を入力する運用とする。
- 読み込み中に書き込みが進む現行ログより、ローテーション済みファイルやスナップショットの利用を推奨する。
- 読み込み開始時のファイルサイズまでを対象とし、実行中の追記は次回に回す。改行で終わらない末尾は保留し、その行の先頭から次回に再読する。保留は累積不正行数に加えない。

## 集計ルール案

### 対象記事

現行の公開HTML出力先である `/blogs/{記事ID}.html` を対象とする。記事IDは正の整数とする。

トップページ、記事一覧、カテゴリ一覧、画像、CSS、管理画面、プレビューは集計対象に含めない。実際の公開URLに別名や書き換えがある場合は、実装前に対応方針を確認する。

### アクセスとして数える条件

以下をすべて満たすログを1アクセスとする案を採用する。

- 指定した対象ホストへのリクエスト。
- HTTPメソッドが `GET`。
- ステータスが `200` または `304`。
- 記事詳細URLに一致する。
- 外部UAルールでクローラーと判定されず、明示的な除外条件にも一致しない。

状態DBには表示期間外も含む日別集計を保存する。期間指定はHTML生成時に適用する。

`304` は再検証リクエストとして含める。一方、ブラウザーキャッシュなどでサーバーへリクエストが届かない閲覧は把握できない。リダイレクト、エラー応答、`HEAD` はアクセス数に含めない。

URIからクエリ文字列を取り除いて記事をまとめる。異なるホストの記事を混在させないため、初期実装では対象ホストを1つ指定する。ホスト名の大小文字やポートの扱いは、入力値とログに対して同じ正規化規則を適用する。

### 期間と日付

- 既定の集計タイムゾーンは `Asia/Tokyo` とし、変更可能にする。
- 日付指定はそのタイムゾーンで解釈する。
- 開始日と終了日は両方を含める。内部では開始日の0時以上、終了日の翌日0時未満として判定する。
- 期間を省略した場合は、入力ログに含まれる対象記事アクセスの全期間を集計する。
- 明示された期間の日別推移は、アクセスがない日も0件として表示する。

### 除外

初期実装では、User-Agentの文字列条件とIPアドレス・CIDRによる明示的な除外を候補とする。自動Bot判定を完全なものとして扱わず、設定した条件と除外件数をレポートに表示する。

IPによる除外は、ログの接続元情報が何を表すかを確認してから採用する。リバースプロキシやCDN経由の場合、任意の転送ヘッダーをそのまま実クライアントIPとして信用しない。

## CLI案

クローラー判定はUser-Agentに対して行い、外部JSONファイルで管理する。詳細は「クローラー判定ルール」を参照する。

```sh
go build -o ./bin/access-report ./cmd/access-report

./bin/access-report \
  --input /var/log/caddy/access.log.json \
  --input /var/log/caddy/access-rotated.log.gz \
  --host example.com \
  --output ./data/access-report/index.html
```

| オプション | 内容 | 既定値 |
| --- | --- | --- |
| `--input` | 入力ファイル。複数回指定可能 | 必須 |
| `--host` | 集計対象ホスト | 必須 |
| `--output` | 出力HTMLファイル | `./data/access-report/index.html` |
| `--blog-db` | タイトル取得用の記事DB。空文字で無効 | `./data/app.db` |
| `--state` | 専用SQLiteファイル | `./data/access-report-state/state.db` |
| `--crawler-rules` | クローラー判定ルールJSON | `./config/access-report-crawlers.json` |

除外条件のオプションは、実ログを確認してから具体化する。クローラー判定用の外部JSON以外の設定ファイル、標準入力、シェル非依存のglob展開は初期実装の必須としない。

### 環境変数

設定の優先順位は **コマンドライン引数 ＞ 環境変数 ＞ コード内の既定値**。引数を省略した場合だけ、対応する環境変数を参照する。空文字を設定した場合も値として扱う（`ACCESS_REPORT_BLOG_DB=` で記事DB参照を無効化）。

| 引数 | 環境変数 |
| --- | --- |
| `--input` | `ACCESS_REPORT_INPUT` |
| `--log-dir` | `ACCESS_REPORT_LOG_DIR` |
| `--log-name` | `ACCESS_REPORT_LOG_NAME` |
| `--host` | `ACCESS_REPORT_HOST` |
| `--state` | `ACCESS_REPORT_STATE` |
| `--output` | `ACCESS_REPORT_OUTPUT` |
| `--crawler-rules` | `ACCESS_REPORT_CRAWLER_RULES` |
| `--blog-db` | `ACCESS_REPORT_BLOG_DB` |

`ACCESS_REPORT_INPUT` は改行区切りで複数ファイルを指定できる（LF・CRLF対応、空行は無視）。`--input` を指定した場合は環境変数の一覧全体を置き換える。`--input` と `--log-dir` の排他制約は、環境変数を反映した後にも適用する。

環境変数で指定した記事DBも明示指定として扱い、存在しない場合はエラーにする。

### クローラー判定ルール

クローラーかどうかはUser-Agent（UA）の文字列から推定する。IPアドレス、逆引きDNS、アクセス頻度による判定は初期対象外とする。UAは自己申告なので、実際のクローラー運営元を認証するものではない。

判定パターンはソースに固定せず、`--crawler-rules` で指定する外部JSONから読み込む。既定の配置案は `config/access-report-crawlers.json`。ルールを編集して次回CLIを実行すれば反映でき、バイナリの再ビルドは不要とする。実行中の再読み込みはしない。

```json
{
  "version": 1,
  "rules": [
    { "id": "googlebot", "name": "Googlebot", "description": "Googlebot", "pattern": "(?i)googlebot", "enabled": true },
    { "id": "bingbot", "name": "Bingbot", "description": "Bingbot", "pattern": "(?i)bingbot", "enabled": true },
    { "id": "generic", "name": "その他のクローラー", "description": "汎用的なクローラー表記", "pattern": "(?i)(bot|crawler|spider|slurp|facebookexternalhit|bingpreview)", "enabled": true }
  ]
}
```

- `version` はファイル形式の版。ルールを編集するたびに増やす番号ではない。
- `id` は一意な管理用ID、`name` は画面に表示する必須のクローラー名、`description` は説明、`pattern` はGoの正規表現、`enabled` は有効・無効の切り替えとする。
- 有効なパターンのいずれかに一致すればクローラーとする。複数ルールに一致しても1リクエストを1回だけ数え、JSONの記載順で最初に一致したルールのIDを保存する。画面にはそのルールのnameとUser-Agentを併記する。汎用ルールは末尾に配置する。
- `(?i)` を付けると大文字・小文字を区別しない。パターンはUA全体への部分一致として評価する。
- 有効ルールが0件ならクローラー判定を無効にする。ファイル欠落時は `cmd/access-report/templates/access-report-crawlers.json` に由来する埋め込み済みの既定ルールを自動作成する。既存ファイルは上書きせず、JSON不正はエラーにする。
- UA欠落・空文字はクローラーにしない。UAが複数値ならログ中の順に半角スペースで連結する。
- 起動時に全ルールを検証する。ファイル欠落、未対応版、未知のキー、ID重複、必須項目欠落、空パターン、不正な正規表現はDB更新前にエラーにする。
- 画面の集約単位は引き続きUser-Agentとし、名前が同じでもUAが異なれば別の行として表示する。名前は生成時に現在の設定から解決するため、nameのみの変更では再集計不要。

#### 差分集計との整合性

有効なルールのID・pattern・記載順を正規化し、集計条件に含める。JSONの空白・キー順、name・descriptionだけの変更では再集計不要。ID・pattern・有効状態・有効ルール順を変更した場合は、名前の選択結果が変わり得るため差分取り込みを拒否する。

ルール変更後は、別の状態DBへ元ログを全件取り込む。現在のDB案では非クローラーのUAと件数を保存しないため、保存済み集計だけで過去を新ルールに分類し直すことはできない。元ログが既に削除されている期間は再分類できない。過去の再分類まで必要になった場合は、全UAの日別件数を保存する方式へ変更する必要がある。

外部ルールファイルと新DBを使って再集計し、HTMLの確認後に運用を切り替える。古い集計に新ルール分だけを混ぜない。

## HTMLレポート

デザイン確認用サンプル：[アクセスレポートHTML](mocks/access-report/index.html)。既存管理画面の濃紺背景・アンバーのアクセント・角丸パネルに合わせ、サンプルログの実集計を表示する。CLIの実装ではなく、外部依存のない単一HTMLである。

### サンプルに追加したクローラー・404タブ

「アクセスレポート」と「クローラー・404」を上位タブで切り替える。それぞれに過去1か月・全期間の切り替えを設ける。

- クローラーによるアクセス：対象ホストの全パス・全メソッド・全ステータスを対象とする。現行サンプルではUser-Agentを大文字・小文字を区別せず `bot|crawler|spider|slurp|facebookexternalhit|bingpreview` で判定する。User-Agent別の件数を表示する。これは自己申告文字列に基づく推定であり、悪意の判定ではない。
- 404ページの一覧：対象ホストで404を返したリクエストを、クエリ文字列を除いたパス別に集計する。全メソッドを含み、クローラーの一覧とも重複し得る。
- 各一覧は件数降順で上位20件を表示し、21件目以降はアコーディオンに格納する。ログ由来の文字列はエスケープし、リンク化しない。
- サンプルではログ最終日を期間の基準とする。全期間はクローラー11,185件、404は36,409件。

差分集計のDBには記事用の集計とは別に、日別User-Agent別のクローラー件数と日別パス別404件数が必要になる。クローラー表示のためUser-Agentの保存が必要になるので、既存の「User-Agentを保存しない」案は記事集計に限定し、追加集計の保存期間・文字列長上限・容量を実装前に確定する。生ログやクエリ文字列は保存しない。スキャン疑い判定用に404アクセスのIPを別テーブルへ保存する。

### 出力構成

単一のHTMLファイルとして出力し、CSSも埋め込む。JavaScript、外部CDN、外部フォントを必要とせず、ローカルでも閲覧できる形とする。

表示は画面サンプルに合わせる。アクセスレポートとクローラー・404の上位タブを設け、各タブで過去1か月・全期間を切り替える。アクセスレポートは観測期間、概要指標、日別推移、記事ランキングをまとめて切り替える。集計条件・処理結果欄や注意書きは画面に設けず、処理件数や異常はCLIの標準エラー出力と状態DBで確認する。

ランキングはアクセス数の降順、同数の場合は記事IDの昇順とする。記事タイトルは記事DBから取得し、取得できないIDは「記事 {ID}」で表示する。記事へのリンク生成は必須にしない。アクセスがない記事の一覧には記事台帳が必要なため、対象外とする。

各行は最初に一致した理由で分類し、処理件数の合計が追えるようにする。不正行、対象ホスト外、対象記事・メソッド・ステータス外、明示的な除外、集計対象の順に判定する。入力全体の累積処理件数と今回の処理件数を分け、表示期間の記事アクセス数とも区別する。

ログ由来の文字列はHTMLテンプレートでエスケープする。生ログとクエリ文字列はHTMLへ出力しない。アクセス元IPはユーザー指定によりスキャン疑い一覧へそのまま表示する。クローラー欄のUser-Agentはテーブル設計の文字列上限とエスケープ規則に従う。入力ファイルの絶対パスも表示しない。

## 出力とエラー処理

- 出力先は既存サイトの `data/publish/` と分け、micro-frontの `publish` 処理から呼び出さない。
- 出力先ディレクトリが存在しない場合は作成する。
- 集計とHTML生成が完了した後、一時ファイルから置き換える。失敗時に既存レポートを壊さない。
- 引数不正、ファイルを開けない、読み込み失敗、gzip破損、HTML出力失敗は異常終了とする。
- JSON不正や必要項目不備は行単位でスキップし、標準エラー出力へ件数を報告し、状態DBに記録する。生のログ行は出力しない。
- 不正行があっても集計できた場合は成功終了とし、スキップ発生を明示する。ただし、有効なアクセスログ行が1件もない場合は異常終了とする。
- 有効なログはあるが対象記事のアクセスが0件の場合は、0件のレポートを正常出力する。

生成HTMLを外部公開するかどうかは運用側で判断する。初期構成ではローカル閲覧を想定し、既存の公開サイトへのコピーや配信設定の追加は行わない。

## 初期実装の対象外

- micro-front管理画面との統合。
- リアルタイム監視とログ追尾。
- セッション数、滞在時間、読了率。
- 高度なBot判定、国別集計、参照元分析。
- 複数サイトの横断レポート。

## 検証方針

実装時には、小さな固定ログを使って集計結果を確認する。

- 記事URLと一覧・画像・プレビューURLの区別。
- クエリ文字列を含む同じ記事の合算。
- ホスト、メソッド、ステータス、除外条件による選別。
- タイムゾーンを考慮した日付境界と終了日の扱い。
- 複数入力、gzip、不正行、末尾の不完全な行の扱い。
- 0件レポートとランキングの順序。
- ログ由来文字列のHTMLエスケープ。
- 出力失敗時に既存HTMLが保持されること。

## 実装前に確認する事項

1. Caddyの設定と匿名化したログサンプルで、JSON形式、日時、ホスト、URI、接続元情報を確認する。
2. 記事が実際に `/blogs/{記事ID}.html` で配信されているか確認する。
3. ローテーション後のファイル名、圧縮形式、保存期間、ログのおおよその容量を確認する。
4. 除外したい自分のアクセスやBotの条件を決める。
5. `200` と `304` を数える案、および日別集計のタイムゾーンを確定する。

差分集計の導入前に、実環境のログ更新・ローテーション方式を確認する。全件再集計は、新しい状態DBへ同じログ一式を取り込む復旧手段として残す。

## 差分生成の設計案

### ユニークアクセス表示の追加検討

HTMLサンプルはアクセス数に加えてユニークアクセス数を表示する。暫定の識別単位はIPアドレス（client_ip、欠落時はremote_ip）とUser-Agentの組み合わせとする。概要は選択期間全体、日別は各日、記事ランキングは各記事・選択期間で重複を除外する。同じアクセス元が複数日に訪問するため、日別のユニーク数を足して期間全体のユニーク数にはできない。

クローラー除外後の実集計では、過去1か月は522アクセス・215ユニーク、全期間は836アクセス・370ユニークとなる（静的モックは除外導入前の表示）。記事レポートには生のIPを出力しないが、スキャン疑い一覧にはユーザー指定によりIPをそのまま表示する。記事用のUser-Agentは識別子生成にのみ利用し、クローラー表示用User-Agentは別集計として扱う。IP欠落時はユニーク数に含めず、件数を管理する。実クライアントIPとして扱えるかはCaddyの配備構成を確認する。

差分集計でこの表示を実現するには、日別・記事別・アクセス元識別子の対応も保存する必要があり、現在の日別カウントのみのDB案では不足する。CLI実装前に、秘密鍵を使ったHMACによる識別子生成、鍵の継続管理、保持期間、期間をまたぐ重複排除の保存設計を追加で確定する。単純ハッシュだけでIPを匿名化できるとは扱わない。HTMLサンプルの生成は一時的な集計であり、アクセス元の識別子はファイルに保存していない。

日時順ではないため、前回の最大日時より新しい行だけを取り込む方式は採用しない。全リクエストを一意に識別するIDも確認できていないため、日時や行内容によるイベント重複排除も採用しない。

### 採用する仕組み

**ファイルごとの処理済みバイト位置と集計値を専用SQLiteに保存し、追記部分だけを取り込む。HTMLは保存済み集計から毎回全体を生成する。**

ランキングや割合は他の記事の増加でも変わるため、HTML自体の部分更新は行わない。古い日時の行でも、未処理位置に追記されていれば取り込む。

SQLiteはmicro-frontの記事DBと分離する。既存GoモジュールのSQLiteドライバーを共有できるが、既存内部パッケージには依存しない。保存処理のソースは `cmd/access-report/state.go` に置く。状態DBは公開対象外の `data/access-report-state/state.db` を既定とする。

| 保存対象 | 主な内容 |
| --- | --- |
| メタデータ | スキーマ版、集計ルール版、集計条件ハッシュ、更新番号 |
| ログ世代 | 内部ID、パス履歴、利用可能ならdevice/inode、照合用ハッシュ、確定オフセット |
| 日別記事集計 | 日付、記事パス、アクセス数 |
| 処理情報 | 世代別の分類件数、観測日時範囲 |

生ログは状態DBに保存しない。記事ユニーク判定は引き続きHMACを使用し、404アクセス元のIPのみスキャン疑い集計用に保存する。記事のユニーク判定にはHMAC識別子を保存し、クローラー一覧用には長さを制限したUser-Agentを保存する。詳細はテーブル設計を参照する。

対象ホスト、タイムゾーン、記事URL判定、対象ステータス、除外条件などを集計条件ハッシュに含める。条件が変わった場合は差分取り込みを拒否し、別の状態DBで全件再集計する。表示期間、出力先、HTMLデザインの変更は再集計不要とする。

### 処理位置と途中の行

確定オフセットは、処理した最後の完全行の改行直後を指す。対象外・除外・不正な完全行もオフセットを進める。改行のない末尾は、JSONとして読めても未確定として次回へ回す。

通常ファイルではJSON解析をオフセットから再開する。既読領域ハッシュ計算のための先頭からの走査は別途行う。gzipでは展開後のバイト位置を保存し、先頭から展開して既読位置まで読み飛ばす。gzipの物理オフセットから直接再開できるとは扱わない。

### ファイル識別とローテーション

パスだけでは識別しない。同じパスが別のログに置き換わる場合と、同じログが改名される場合を区別する。

- 通常の追記：ファイル識別情報と、先頭・確定位置直前の一定範囲のハッシュを照合して再開する。
- rename方式：旧ファイルの未処理末尾を取り込み、新しい現行ファイルは別世代として0から処理する。旧ファイルも入力に含める。
- コピー・gzip化：識別情報が変わるため、展開後の既読領域全体のSHA-256と長さを保存値と照合する。一致すれば同じ世代の継続候補とする。必要な全体ハッシュは初回読み込み時に計算し、差分追記時は既読部分の走査も必要になるため、ハッシュ計算コストと再開用状態の保存方法は実装時に評価する。
- 照合が曖昧：自動統合や新規加算をせず停止する。内容が同一の別ログとコピーを内容だけで区別することはできない。
- サイズ縮小・照合不一致：切り詰めや差し替えとして停止する。自動で0から再加算しない。

通常の追記確認で使用する部分ハッシュは、既読領域全体の変更検出を保証しない。入力は追記専用で、既読部分を変更しないことを前提とする。ファイル名だけでの推測や、先頭数行だけを根拠にしたコピー判定は行わない。

copytruncate方式では、前回実行後の未処理末尾が退避ログに残っていなければ復元できない。初期の対応運用はrename方式を基本とし、実際にcopytruncateを使用している場合は追加設計する。

入力から以前の世代が消えた場合は、取り込み漏れの可能性を警告する。ローテーション済みファイルは少なくとも次回の取り込み完了まで保存する。保持期限切れによるログ消失を、この仕組みだけで検出・復元できるとは保証しない。

既存の「別ファイル間の同一リクエストを自動排除しない」方針は維持する。ただし、取り込み済みファイルの改名・コピー・圧縮を同じログ世代として認識し、ファイル単位の二重取り込みを防ぐ。異なる世代間で部分的に重複するログは入力しない運用とする。

### 整合性と障害復旧

1. 同じ状態DBを同時に使用するプロセスは存在しない前提とし、アプリケーションの排他ロックは設けない。
2. 条件・ログ世代を照合し、今回読むファイルサイズを確定する。
3. ファイルごとに差分を読み、集計する。
4. 集計値、分類件数、確定オフセット、照合用情報を同一DBトランザクションで保存する。
5. 全入力の処理成功後、保存済み集計からHTMLを一時ファイルへ生成し、置き換える。

読み込み中に失敗したファイルはロールバックする。先行ファイルのコミット済み内容は残すが、その実行ではHTMLを更新せず異常終了する。再実行では保存済み位置から継続する。

DBコミット後にHTML出力が失敗しても、再実行時に同じログを加算しない。新規行がない場合も、保存済み集計からHTMLを再生成する。DBとHTMLの同時更新は保証せず、HTMLのmeta要素に集計更新番号を記録して区別する。

状態が既にある場合、今回新たな有効行が0件でも既存集計を表示できるものとする。初回に有効なログが全くない場合は従来どおり異常終了する。

状態DB消失時は保持しているログ全体から再構築する。ログが残っていない期間は復元できない。DBバックアップはCLI停止中、またはSQLiteに対応した方法で行う。集計条件変更時も別の状態DBと出力先で再集計し、成功後に切り替える。

### 差分処理の検証

- 同じログを2回処理しても集計値と累積分類件数が増えない。
- 古い日時の追記も取り込まれる。
- 不完全な末尾が完成すると1回だけ取り込まれる。
- rename後の旧ファイル末尾と新ファイルを両方処理できる。
- コピー・gzip化した取り込み済みログを再加算しない。
- 切り詰め、照合不一致、曖昧な識別では停止する。
- 保存前後の中断、HTML出力失敗、再実行で二重計上しない。
- 集計条件変更を拒否し、表示期間変更は保存済み集計に反映できる。
- 全件集計と複数回の差分集計の最終結果が一致する。

### 追加で確認する運用条件

提供されたCaddyfileから、以下を運用前提にする。

| 項目 | 設定・判断 |
| --- | --- |
| 現行ログ | `/var/log/caddy/access.log.json` |
| サイズによるローリング | `roll_size 50mb` |
| 退避ログの保持数 | `roll_keep 5` |
| 退避ログの保持期限 | `roll_keep_for 120d` |
| 圧縮 | `roll_uncompressed` がないため、既定のgzip圧縮を想定 |
| 対象ホスト | `modern-utopia.net` |
| 公開記事 | `/sites/blog` の静的ファイル。記事パスの書き換え設定なし |

`import log` はブログのサイトブロックだけにあり、提示設定では管理画面や他サービスに同じアクセスログ設定は適用されない。ただしCLIでもホストを確認する。

Caddy標準のファイル出力は退避時にファイルを改名する方式であり、本案のrename方式に対応する。圧縮された旧世代も探索・照合対象にする。保持数と保持期限の両方が適用されるため、120日間のログ保存を保証する設定ではない。大量アクセスでローリングが進むと、120日未満でも古い世代が削除される。

参照：[Caddy公式 logディレクティブ（file）](https://caddyserver.com/docs/caddyfile/directives/log#file)。退避ファイル名はCaddyのバージョンで異なり得るため、使用バージョンと実際の退避ファイル名は追加確認する。

### ディレクトリ探索の追加案

運用時は現行ログだけでなく、同じログ系列の退避ファイルを毎回自動探索する。CLIに `--log-dir` と `--log-name` を追加する案とし、前者を `/var/log/caddy`、後者を `access.log.json` として利用する。明示的な `--input` との同時指定は拒否する。

- 指定ログ系列の現行・非圧縮退避・gzip退避ファイルを候補とする。他サービスのログは含めない。
- ファイル名は候補選択に使い、処理済み世代との同一性は内容でも照合する。
- 完了した退避世代は再加算せず、未処理の旧世代を処理してから現行世代を処理する。
- 探索中のrenameや圧縮でファイルが消えた場合は再探索する。再試行回数に上限を設け、解決しなければ異常終了する。
- 圧縮途中のgzipを完全なログとみなさず、読み込み・整合性検証に失敗した世代はコミットしない。
- 読み込み中に現行ログが退避へ変わった場合も、開いたファイルとDBの世代を対応させる。実行開始時のサイズ以降は次回に取り込む。

初期の定期実行候補は1時間ごととする。ただし、ログ増加速度と停止可能時間を実測して決める。前回の取り込み以降に未処理世代が保持数・期限の制限で削除されないことが必要であり、実行間隔だけで完全性を保証しない。取り込み済みの集計値は、元ログが削除されてもDBに残る。

残る確認事項は、Caddyのバージョン、実際の退避ファイル名、CLIへのログ共有方法（同一ホスト・コンテナ共有・コピー）、ログ量と定期実行間隔である。


## 実装済みの使い方

```sh
go build -o ./bin/access-report ./cmd/access-report
./bin/access-report --input sample/access.log.json --host modern-utopia.net

# 現行・退避・gzipを同じログ系列として自動探索
./bin/access-report --log-dir /var/log/caddy --log-name access.log.json --host modern-utopia.net

# ルール変更後は別のDB・出力先へ再集計
./bin/access-report --log-dir /var/log/caddy --host modern-utopia.net \
  --state ./data/access-report-next/state.db \
  --output ./data/access-report-next/index.html
```

- テンプレートはモックHTMLをコピーし、CSSと画面構造を維持して繰り返し・表示値だけをGoテンプレートへ置換した。
- 2種類の上位タブ、過去1か月・全期間、日別グラフ、ユニーク数、21件目以降の折りたたみを出力する。
- 全期間は取り込み済みログの最初の日から最後の日までを表示し、過去1か月は最後の日を基準にする。
- クローラールールは起動時に検証する。意味を持つ有効パターン集合が変わる場合は既存DBへの差分取り込みを拒否する。
- DBは1ホスト・1条件。識別用HMAC鍵はDBと同じ場所の `<DBファイル名>.visitor.key` に生成する。鍵とDBは同じ組み合わせでバックアップする。
- 確定オフセットと既読領域全体のSHA-256を保存する。先頭最大4KiBのハッシュで候補を絞り、既読全体のハッシュで確定する。末尾部分ハッシュとハッシュ内部状態は使用しない。ハッシュ照合のため既読バイトも走査する。
- Caddyの世代判定は、現行ファイル名の拡張子前に `-` と退避識別子が入る系列を対象にする。例：`access.log-*.json` / `access.log-*.json.gz`。
- ディレクトリ探索時のファイル消失や圧縮途中のエラーは最大3回再探索する。解決しない場合はHTMLを更新せず異常終了する。
- 同一inodeの切り詰め・内容変更、曖昧な世代照合、完了世代への追記は停止する。copytruncateは対応対象外。
- 不正な完全行は件数を記録してスキップする。1行16MiB超は異常終了する。改行のない末尾は次回へ保留する。
- 自分のIPや任意UAによる追加除外オプションは未実装。記事アクセス数・ユニーク数からは外部UAルールで判定したクローラーを除外する。日別・ランキング・平均・記事数にも同じ条件を適用する。
- クローラー除外後、サンプル全件で記事836件・370ユニーク・記事からの除外609件・クローラー11,185件を確認。404はホストの既定ポートも正規化して数えるため36,411件（モック生成時のホスト文字列完全一致では36,409件）。

### 記事タイトル表示

`--blog-db` の既定値は `./data/app.db`。記事DBをSQLiteの `mode=ro` で開き、`blogs.id` と `blogs.title` のみを参照する。既存のstore初期化・マイグレーションは呼ばない。明示指定したDBがない場合や読み取り失敗時はエラーとし、既定パスが存在しない場合は記事ID表示へ戻す。`--blog-db ""` で参照を無効にできる。

タイトルはHTML生成時に取得し、状態DBには保存しない。タイトル変更後もログ再取り込み・集計条件変更は不要で、再実行すれば更新される。記事DBにない記事・空タイトルは「記事 {ID}」で表示し、全期間・過去1か月、上位20件・折りたたみ内で同じ規則を使う。

記事クローラー除外の導入に伴い集計ルール版を2へ変更した。版1の状態DBへの追記は拒否するため、新しい状態DBへ元ログを全件取り込み直す。クローラー・404側には従来どおり対象リクエストを含める。

クローラー名対応ではスキーマ版を2へ更新し、crawler_agents.rule_idを追加した。旧スキーマは別DBへ全件再集計して切り替える。nameは表示時に解決するため名前変更だけではログ再処理は不要。

## 脆弱性スキャンの疑い

「クローラー・404」タブに追加する。対象ホストの404をIP単位で集計し、同じ集計日内で404件数が100件以上、かつ異なるパスが20種類以上の場合に検出する。UA名や既存クローラー判定とは独立し、UA変更でも同じIPとして扱う。パスはクエリ文字列を除いて数え、IP欠落行はこの判定だけ対象外にする。IPはclient_ip優先、無効・欠落時はremote_ipを使用する。

一覧はIP、選択期間の404件数・パス種類数、条件を満たした日数、検出日の最多件数、期間内の最初・最後の観測日時を表示する。各行を開くと対象パスとUAの上位5件を確認できる。20アクセス元を超える分は折りたたむ。IPアドレスはユーザー指定により伏せずに表示・保存する。共有IPの複数利用者や正規クローラーも条件を満たし得るため、表示はスキャンの断定ではなく推定とする。

タイムゾーンは `Asia/Tokyo`、しきい値は404件数100件・パス種類数20種類とし、`cmd/access-report/main.go` 冒頭の定数 `reportTimezone`・`scanMin404`・`scanMinPaths` で管理する。しきい値は表示条件なので、変更後の再ビルド・再実行で反映でき、再取り込みは不要。1日単位の両条件を満たしたアクセス元を抽出し、そのIPの選択期間全体の404を表示する。期間をまたいだ日別の合計だけで検出せず、異なる日に50件ずつの場合は既定条件を満たさない。

スキーマ版3でIP別・日別・パス別の404件数と観測日時、UA別件数を追加保存する。従来のパス別404だけからIP別データは復元できないため、旧DBは元ログから別DBへ再集計して切り替える。記事アクセス・ユニーク・クローラー件数の条件は変更しない。
